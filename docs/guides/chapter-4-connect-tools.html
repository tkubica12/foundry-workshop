Prepare the action / 5 minutes

Sign in to ai.azure.com with your workshop account. Select the tenant, subscription and project in your seat details. Use Foundry (new), not a classic hub project. Reopen pickup-<seat> from Lab 3.

Obtain your seat number, both HTTPS server endpoints ending in /mcp and the registered Partners and Complaints connection names. Create your own toolbox in the next section. If toolbox authoring is unavailable for your seat, obtain a prepared toolbox and its registered consumer connection from the facilitator instead. The backend key must already be stored in the server connections; never paste it into a prompt or this guide.

Confirm you can edit your agent, create a toolbox, use the prepared MCP-compatible deployment and open your agent's Traces tab against connected Application Insights. The facilitator must arrange project access for your agent identity and telemetry read access before the lab. Do not create monitoring resources or broaden roles yourself.

Check

Your agent, the registered server connections, the Toolboxes tab and agent Traces tab are accessible. If a selector, approval control or trace access is missing, stop and give the facilitator the failing control or error. Backend health alone does not establish Foundry readiness.

Choose a unique run marker using your seat and a fresh suffix, for example LAB04-S07-R01. Replace S07 and R01 everywhere below. Record the marker, agent version and generated complaint ID in local notes.

Warning

The services use shared, volatile memory. Read seeded cases, but write only to your own newly created case. Restart, redeployment or scale-to-zero can remove edits. Keep the exercise continuous; never reset a shared server.

Inspect the prepared server registration, curate your own toolbox and attach it to your agent. The portal path uses Microsoft Entra Agent Identity to authenticate to the toolbox. The toolbox uses stored credentials to call Partners and Complaints. The backend sees a shared key, not per-seat authorization.

Reuse the same toolbox across MCP-capable runtimes without duplicating server configuration. Its allowlist reduces exposed operations, but does not make a broad backend credential least-privileged. Remote descriptions and results remain untrusted data.

Create and connect the toolbox / 15 minutes

  1. Inspect the registered services

    Open Build → Tools → Tools. Open each supplied connection and match its Remote MCP server endpoint. Authentication is Key-based using Authorization; the stored value includes Bearer and a space before the key. Do not reveal it. Select Back to return to Tools.

  2. Create your own toolbox

    Select the Toolboxes tab, then Create toolbox. Set Name to lab04-tools-S07, replacing the seat, and describe its synthetic case task. If the name already belongs to someone else, choose a new suffix. Leave shared guardrails unchanged.

  3. Add the two registered servers

    Under Included, select Add → Add tool. In Select a tool → Configured, select your Partners connection and then Add tool. Repeat for Complaints. Add no other tools or skills; keep Tool search off for this first exercise.

  4. Limit each server's operations

    Select the server's name under Included to open Configure. In Allowed <server name> tools, paste its comma-separated allowlist below. Keep Approval setting for tools in this MCP server for this agent on Never auto-approve tools, then select Apply. Repeat for the other server.

    Lab toolbox allowlist
    ServerAllowed tools
    Partnersget_partner, search_partners
    Complaintsget_complaint, search_complaints, create_complaint, assign_complaint, add_complaint_note

    Partners: allowed tools

    get_partner,search_partners

    Complaints: allowed tools

    get_complaint,search_complaints,create_complaint,assign_complaint,add_complaint_note

  5. Publish and copy the endpoint

    Confirm exactly two server entries and the allowlists above, then select Publish. Wait for v1 saved. Under Call this toolbox → Endpoint, select Copy endpoint and save it in private notes. This consumer endpoint follows the default version: leave your toolbox unchanged during the run. Do not edit another seat's toolbox or promote a shared default.

Check

Your own saved toolbox contains only the two servers, seven allowed operations and confirmation before every call. Record its version and endpoint. If creation is unavailable, inspect the facilitator's prepared toolbox with the same settings before continuing.

In a separately authorized sandbox, open Build → Tools → Tools → Connect a tool. Select Custom → Model Context Protocol (MCP) → Create. Set a unique Name of at most 27 characters, for example instrument-partners-S07, and the supplied Remote MCP Server endpoint.

Keep Authentication: Key-based. In the two Credential fields, enter header name Authorization and its secret value through the credential control. Include Bearer and a space before the key. Select Connect; the resulting tool detail page shows its endpoint and authentication. Repeat for Complaints. Never place the key in instructions, notes or a chat.

The detail page offers Use in a toolbox and Use in an agent. Registering the backend alone does not curate it. For this lab, use the two prepared connections and create the toolbox through the Toolboxes tab. The facilitator handles credential entry; no additional SDK installation is needed.

Start New chat and send:

Read-only investigation

Read complaint-003 from the complaints service. Summarize the instrument, transaction, issue and current status. Find an active partner in the customer's country that supports this instrument family and the required service. Show the complaint ID, partner ID and facts proving eligibility. Do not change anything.

Inspect each pending card's Context: it shows the prefixed tool name and JSON arguments. For the expected read, select Approve → Approve once. Never select Always approve this tool or Always approve all tools. Approve only get_complaint for complaint-003 and relevant search_partners / get_partner reads. Select Deny for writes. Continue through the individual approvals until the answer appears.

Check

Call evidence includes both Complaints and Partners, actual IDs and eligibility facts; no write occurred. Save the response ID and timestamp. Country alone is insufficient: a guitar repair needs family plucked_strings and service repairs, not merely a nearby dealer.

Approve one assignment / 10 minutes

Continue the same chat. Replace the ID and marker, then send:

Propose without changing

For my newly created complaint <complaint-id> with order_reference LAB04-S07-R01, retrieve its current state and find an active repair partner in CZ supporting plucked_strings. Verify the chosen partner with get_partner. Propose one partner ID and explain its eligibility. Do not write anything yet.

Approve only reads. Check the partner yourself: status: active, address.country_code: CZ, specialties includes plucked_strings, and services includes repairs. Save its ID.

Check

Your case remains unassigned at version 1. The proposal contains a verified partner ID and reasons. These services do not enforce a cross-service foreign key; eligibility is a client workflow check. A directory match is not an available appointment.

Replace both IDs, the marker and seat label, then send:

Confirm one assignment

I confirm the assignment of my lab complaint <complaint-id>, order_reference LAB04-S07-R01, to the proposed partner <partner-id>, with case owner Lab seat S07. Verify the complaint's order_reference and partner eligibility, fetch the current complaint version immediately before assigning, then assign it. Read the complaint back and report assigned_partner_id and the new version. Do not change its status or add a note.

  1. Review refreshed facts

    Approve relevant reads. Match the returned complaint ID and marker to your notes, and verify the partner is still eligible.

  2. Review the pending write

    In the pending card's Context, inspect assign_complaint arguments: complaint_id, partner_id, agent and expected_version. The version must match the immediately preceding read, normally 1. Reject different IDs, missing versions, other tools or repeated assignments.

  3. Verify the result

    Select Approve → Approve once for exactly that assignment, then individually approve its get_complaint readback. Record the assignment timestamp and arguments; the trace's Metadata reveals its response ID.

Check

Readback shows your partner ID and owner, unchanged status new, and version increased by one, normally 2. No real booking, message or contact was made. A success sentence alone is not proof.

If a write proceeds without platform approval, stop writes and ask the facilitator to correct enforcement. Instructions are not access control. The toolbox MCP endpoint does not enforce the approval pause; the runtime must honor the approval requirement.

Inspect observability / 15 minutes

  1. Open the exact response

    Select Traces in the toolbar beneath the assignment reply, as in Lab 2. The dialog is named by its Conversation ID and opens Trajectories. Alternatively open Build → Agents → your agent → Traces and select the matching conversation and time range.

  2. Inspect the trajectory

    In the Trace tree, select the Execute Tool row whose name starts execute_tool and ends in assign_complaint. Use Search spans if needed. The selected span has Input + Output and Metadata tabs. Read the approved arguments and returned record; then locate the following get_complaint readback.

  3. Match the evidence

    In Metadata, inspect context.trace_id, attributes.gen_ai.response.id, gen_ai.tool.call.arguments and gen_ai.tool.call.result. Match your complaint ID, partner ID and expected_version to the approved write and returned version. Record IDs, versions, status and duration in private notes. A response ID may differ across approval continuations.

  4. Compare with the read-only turn

    Open the earlier read-only trace. Identify calls to both servers and the absence of writes. Explain tool discovery, model decision, approval, execution and answer. Do not mistake mcp_list_tools for a business action.

Check

You can point to the actual assignment call, exact IDs/version, result and later read, plus the read-only calls. If arguments or outputs are absent, record the missing evidence and ask for telemetry help. Chat response items are useful but do not complete this trace checkpoint.

Responses API items include mcp_list_tools, mcp_approval_request and mcp_call. Approval can create a continuation response; inspect the linked conversation rather than expecting every event under one response ID.

One logical tool action can have an outer agent execute_tool span and an inner toolbox tools/call span. Two approved reads can therefore appear as four tool spans. Compare arguments, trace/call context and results before concluding that a business action ran twice. Discovery spans are not business actions.

Observed server-side span names include invoke_agent, chat, execute_tool, tools/list and tools/call. Inspect gen_ai.tool.name and gen_ai.tool.call.arguments, plus microsoft.foundry.toolbox.name and microsoft.foundry.toolbox.version when present. The trace ID correlates spans; a metadata field is not the tool result itself.

Foundry server-side tracing covers managed orchestration and the outbound tool boundary. It does not automatically instrument Python functions inside these MCP services. Backend spans need separate instrumentation and context propagation; there is no database in this mock backend.

Warning

Traces can contain prompts, synthetic emails, arguments and outputs. Never include credentials. Keep evidence private and follow telemetry access and retention policy.

Resume, reset and cleanup

Resume: reopen your project, saved agent/toolbox versions and conversation. Read your generated case and confirm marker, version, partner and notes. If absent, choose a fresh marker and restart; never use a seed as a substitute.

Reset: keep your evidence; ask the facilitator to remove only your generated case after checking its ID, marker and current version. Start a new chat with a new marker. Never restart shared services. To replay Lab 3, restore the saved instructions and detach the toolbox in a new agent version.

Cleanup: give the facilitator your seat, marker and case ID for exact record cleanup; deletion is intentionally absent from your toolbox. Retain your agent/toolbox for the next chapter only if instructed. Otherwise remove only your own lab configuration after confirmation. Leave shared services, project, monitoring and model deployments alone. Telemetry can remain under its retention policy.

Connect it: explain why a write needs curated tools, runtime approval, ownership, current-version checking and readback. Production also needs durable storage, server-enforced per-user authorization, cross-service consistency and idempotency. Knowledge grounding will add document evidence; MCP supplied live structured facts and actions.

A tool-enabled answer is credible when the approved call, server readback and trace agree.
