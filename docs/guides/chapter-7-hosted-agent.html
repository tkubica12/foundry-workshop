Prepare / 5 minutes

This lab is optional. Complete the Lab 4 tool preflight first. Use fictional instrument-service records only. Lab 6 is the final mandatory lab; this specialist demonstrates another implementation path, not a replacement for managed Memory.

See it: watch a short facilitator run: a pending read, one approved call, a verified answer and the matching trace. Compare it with Lab 4: the business tools are the same, but the model/tool loop and approval boundary now live in your LangGraph code. Use the remaining core time to deploy and inspect your own instance.

  1. Sign in to portal.azure.com with the assigned workshop account. Open Cloud Shell in the top navigation and choose PowerShell. In Getting started, select No storage account required, select your assigned subscription and choose Apply. Confirm the ephemeral-session notice. If an existing profile mounts storage, download any files you need before using Settings → Reset User Settings to return to setup. Do not restart an existing session with unsaved work.

  2. Use the setup command below. Azure CLI, PowerShell and Git are already installed in Cloud Shell; you do not install Python, SDK packages, uv, Docker or tools on your computer. Compare the printed tenant and subscription with your private seat assignment. If the subscription differs, run az account set --subscription YOUR-ASSIGNED-SUBSCRIPTION with the assigned value. Never substitute an administrator account.

  3. Use Manage files → Upload to upload the facilitator-provided seat.config.json into your Cloud Shell home directory. Move it with the assignment command below. Open it with code $config and verify the project URL, project ARM ID, unique lab07-<run>-sNN name, existing model deployment, pinned toolbox endpoint and immutable image digest. The file contains private resource identifiers, not literal credentials; never publish it.

  4. Confirm the facilitator has qualified Hosted Agent capacity, runtime model/tool permissions and connected Application Insights. For deployment, confirm Foundry Project Manager; for trace viewing, confirm the assigned monitoring read access. Registry and identity setup are prepared, not part of the core lab.

Read the code / 7 minutes

Open code student\labs\hosted-agent\agent.py in the Cloud Shell editor and read the adjacent system-prompt.txt. Find build_graph, select_tools, approve_call and serve. LangChain's create_agent factory builds the LangGraph; ResponsesHostServer adapts that compiled graph to Foundry's Responses protocol. Python runs inside the published image, not in your deployment client.

  1. Follow the model → tool decision → approval interrupt → MCP result → answer path. The system prompt asks for verified complaint and partner facts. The interceptor stops execution before the remote call.

  2. Compare the seven tool names with Lab 4. Four reads require individual approval. The three write tools remain discoverable but fail with LAB07_WRITE_DENIED, even if a user asks for them. Do not edit shared seed records.

  3. Find the hosted FoundryCheckpointSaver and AzureAIOpenTelemetryTracer. Checkpoint storage preserves pending approvals; telemetry records execution. Neither is the user-profile or chat-summary Memory from Lab 6.

Check

Explain why changing the prompt cannot bypass the write boundary, and why approval state must outlive one HTTP request.

GitHub Actions builds Linux/amd64 from the hashed lock, tests the actual Responses host with an offline fixture and publishes to GHCR. Your seat consumes a verified digest, not latest. The facilitator verifies that the runtime source in this workshop checkout matches the image's recorded source commit; newer delivery scripts do not change the agent in an already published image. Stop if the source or digest differs from the prepared assignment. Offline tests prove protocol behavior; only live model/tool calls and recorded traces establish the cloud path.

Deploy / 8 minutes target

Review the scope printed by preflight. The PowerShell wrapper sends az rest requests to Foundry API v1, with audience https://ai.azure.com. It creates only your isolated agent version; it does not deploy models, change roles or rebuild the MCP backends. The container advertises Responses protocol 2.0.0.

Authorize your assigned version

& $lab -Operation deploy -Config $config -State $state -Confirm

Wait for status active. Polling is bounded to ten minutes; this is not a latency guarantee. Open ai.azure.com, select the assigned project and find the exact name under Build → Agents. Compare its version and hosted definition with your local receipt.

Check

Record the agent name, version and image digest privately. Active infrastructure is not proof that the model or MCP path works. If deployment exceeds the target, use the recovery path rather than consume the trace-inspection time.

Create a personal recovery archive

& $lab -Operation backup -Config $config -State $state

Copy the printed Backup path into Manage files → Download. Save the ZIP privately on your computer and confirm the download completed. It contains configuration, ownership state, conversations and uncertain-operation markers, not credentials. Creating a ZIP in Cloud Shell alone does not preserve it. Repeat this backup and download after each invocation and cleanup; keep the newest archive.

Approve a read / 10 minutes

Use the same Azure CLI wrapper for the Responses API. Its fixed read-only prompt retrieves complaint-003 and partner-055 through the Lab 4 tools. Review their actual facts; the prompt does not authorize assigning a partner.

Start a new read-only conversation

& $lab -Operation start -Config $config -State $state -Conversation $read

  1. Read the requested tool name and JSON arguments in Review. Expand the JSON arguments value to find the business tool and its record ID. Check that it is a read of the intended synthetic complaint or partner. Copy the printed Approval ID, not the internal interrupt ID.

  2. Replace APPROVAL-ID in the next command with that exact ID. Approve only after reviewing the call. Repeat with each newly printed ID; never reuse an earlier ID or approve all future calls.

Approve the displayed call once

& $lab -Operation approve -Config $config -State $state -Conversation $read -ApprovalId APPROVAL-ID

After the approved answer, start a separate conversation with the command below. For its first pending read, use its current Approval ID in the rejection command. Expect a failed response with interrupt_rejected and exit code 1; this deliberate denial is not a successful tool call. Keep both conversations for trace inspection. Back up and download the receipts after each turn.

Start an isolated rejection test

& $lab -Operation start -Config $config -State $state -Conversation $reject

Reject its displayed read

& $lab -Operation reject -Config $config -State $state -Conversation $reject -ApprovalId APPROVAL-ID
Check

The approved answer includes complaint-003, a returned partner ID and active/country/instrument/service eligibility facts. The rejected conversation fails explicitly. The next section verifies the answer against actual tool results; a plausible answer alone does not pass.

Connect the traces / 10 minutes

  1. Record the printed Response ID and Trace ID for the initial turn and each approval continuation. Open the selected agent's Traces view in Foundry. Search by Response ID or Trace ID and widen the time window if needed.

  2. Open the connected Application Insights resource in the assigned Azure portal subscription. Under Investigate → Transaction search, find the request by its operation/trace ID. Compare the hosting request, LangGraph execution, model call and MCP tool spans within each turn.

  3. Find a complaint-service call and a partner-service call. Compare tool name, arguments, result and duration with the terminal's approvals and the final answer. Approval continuation is another HTTP turn and can have a different trace; link turns using their saved Responses chain, not by claiming one trace spans every approval.

  4. Confirm a rejected turn has no executed MCP call after the rejection. If spans or content are absent, distinguish missing viewer access, ingestion delay and instrumentation/export failure. Do not replace a missing trace with an inferred success.

An approval interrupt can appear as a stopped or failed tool span without a tool result. That does not prove remote execution. Verify the successful resumed span and its recorded result; do not count duplicate instrumentation spans as separate business calls.

Content recording is enabled only in a facilitator-approved synthetic environment. Model identities, runtime identities and trace-reader permissions are separate responsibilities. Never turn on content capture for private business data as a shortcut.

Check

Show actual model and tool evidence tied to your response. Explain which boundary is managed by Foundry and which behavior remains your code's responsibility.

Reset and cleanup / 5 minutes

Activation timeout: run the status command. Failed activation or runtime 403: retain your receipts and ask the facilitator to check provisioning or the dedicated agent identity. Do not create substitute resources or grant broad permissions.

Inspect the existing version

& $lab -Operation status -Config $config -State $state

Uncertain create or turn: stop if a receipt says create-requested without a version, or a .pending.json file remains after a client error. Give the facilitator the correlation or trace ID. Do not delete the receipt and replay blindly. Reset: use a new conversation filename such as read-2.json; leave old evidence intact. Resume: keep the same conversation file and use only its current approval ID.

Conversation locked: wait for the owning command. After a confirmed terminated process, ask the facilitator to inspect the pending receipt and live response before removing that exact lock; do not remove a live command's lock.

If the state records create-requested with no version, ask the facilitator to inspect the assigned agent and run the command below. It accepts exactly one live version with matching ownership, configuration fingerprint and image; it never sends a create request. If no unique match exists, stop and preserve the state rather than deleting it.

Recover the existing matching version

& $lab -Operation recover-create -Config $config -State $state

Start a new ephemeral PowerShell shell and clone the repository again with the setup command. Upload your newest personal recovery ZIP using Manage files → Upload. Replace YOUR-DOWNLOADED-ARCHIVE.zip below with its uploaded filename. Expand only your own trusted archive, into the empty seat directory; never overwrite newer receipts.

When finished, compare your deployment receipt with your assigned name. The next command deletes only the recorded version and its sessions, checks that it is absent and can be repeated safely. It never sends a parent-agent DELETE. Other versions, shared toolbox, MCP backends, connections, registry, image and roles are not targeted. Deleting the last version can make the parent disappear from the service.

Delete only your recorded version

& $lab -Operation cleanup -Config $config -State $state -Confirm
& $lab -Operation backup -Config $config -State $state

See PASS: owned version absent. Download the final archive using its printed Backup path, then close all Cloud Shell session windows. Closing the shell is not agent cleanup.

Checkpoint and monitoring retention are separate from version deletion. Leave shared data-retention cleanup to the facilitator; never delete a shared project or registry.

In your own authorized fork, edit the system prompt or graph in a browser editor, publish through GitHub Actions and consume the new verified digest in a new seat configuration/name. The workflow tests the image; a separate developer environment can run the Python tests. Keep existing evidence and do not overwrite another seat. A code change requires a new image: changing a file in Cloud Shell does not modify the running container. Keep write-tool extensions out of this lab's scope.
